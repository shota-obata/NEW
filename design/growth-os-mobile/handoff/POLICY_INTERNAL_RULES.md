# 社内規定：就業規則 追加条文（全9条）と、「閲覧」の例外

Growth OSでは、閲覧履歴は本人に全部開きます（誰が・いつ・何を見たか）。誰も見ていない月は「誰も見ていません」と表示します。

**例外は1つだけです。** 運営者（Management）の「閲覧」画面 — 指導者（Support）から従業員（Staff）への返答内容と返答日数 — でのアクセスは、本人にも指導者にも出しません。

当人に知らせずに見る仕組みなので、**先に規定に書き、周知し、全員の同意を取り、それから開きます。** 順番を逆にしません。

## 出典

条文の出典は **`就業規則 追加条文 草案.dc.html`（全9条）** に一本化しています。このファイルは、その草案を実装側から読むための対応表です。**条文そのものを直すときは草案を直してください。ここは写しです。**

条文の用語と、アプリ側の役割名の対応：

| 条文 | アプリ | 備考 |
| --- | --- | --- |
| 従業員 | Staff | 記録を作成する者 |
| 指導者 | Support | 助言し、到達を判断する者 |
| 運営者 | Management | 育成の体制・設計を管理する者 |

対応する画面：`Growth OS Mobile.dc.html` の `13a`（同意）、`13b`（全文）、`13c`（開くための3条件）、`13d`（時間外）、`12f`（ロック状態と解錠）、`12g`（条文と手順）。

## 1. この例外の根拠（第5条・第6条）

> **第5条（閲覧履歴の開示）**
>
> 1　会社は、従業員が作成した記録について、何人がいつ閲覧したかを当該従業員に開示する。
>
> 2　前項の定めにかかわらず、次条に定める確認については開示の対象としない。

> **第6条（指導内容の確認）**
>
> 1　会社は、指導の質を確保し、育成の体制を適正に保つため、指導者が従業員に対して行った返答の内容および返答までに要した日数を確認することがある。
>
> 2　前項の確認は運営者の区分に属する者のみが行い、その目的は指導の体制および担当の割り当ての見直しに限る。従業員個人の評価を目的として行わない。
>
> 3　第1項の確認は、対象となる従業員および指導者に対して個別に通知せず、第5条第1項の開示の対象としない。これは、確認の事実を知らせることにより指導者の返答が本来の判断と異なるものとなり、確認の目的を達し得なくなることを避けるためである。
>
> 4　第1項の確認を行うことができる者は、運営者の区分に属する者に限る。
>
> 5　第1項に基づく指導者への指示は、傾向を示す数値をもって行い、個別の返答文を引用しない。
>
> 6　会社は、第1項の確認の対象、目的および期間について、年1回、従業員代表との話し合いの場で確認する。
>
> 7　従業員は、本条の運用に疑義があるときは、第1項の確認の停止を求めることができる。求めがあったときは、会社は理由を書面で示す。
>
> 8　会社は、第1項の確認を行うことがある旨を、本規定の周知をもってあらかじめ全従業員に明らかにする。

**コード内で例外を通す箇所には、必ずこの形のコメントを置きます。**

```
// 就業規則 第6条第3項に基づく例外。第5条第1項の開示対象から除外する。変更には規定の改定が必要。
```

## 2. なぜ例外を置くのか

閲覧が本人に見えると、指導者は「見られる前提の返答」を書きます。手順を渡す返答が減らないのは、たいていこれが理由です。直したいのは設計であって人ではないので、当人の目には入れません。理由まで含めて第6条第3項に書いてあります。

例外を1つ作る代わりに、歯止めを6つ足します。

| 歯止め | 条項 |
| --- | --- |
| 従業員個人の評価を目的としない | 第6条第2項 |
| 運営者に限る | 第6条第2項・第4項 |
| 個別の返答文を引用しない（渡すのは数字だけ） | 第6条第5項 |
| 年1回、従業員代表と確認する | 第6条第6項 |
| 従業員が停止を求められる | 第6条第7項 |
| 周知が前提（周知していない規定は効力を持たない） | 第6条第8項・第9条 |

## 3. 開けるまでの手順（この順番で）

1. **条文を確定する** — ✅ **完了**。全9条を就業規則に追加し、第6条について社会保険労務士の確認を受けました。従業員代表の意見書も取得済みです。**常時10人未満の事業場のため、所轄労働基準監督署への届出は不要**で、書面の交付により周知します（第9条・附則）。
2. **周知する** — ✅ **完了**。2026-08-01 の全体通達で全員の受信ボックスに残し（消去しても30日は戻せます）、書面も交付しました。指導者には、自分の返答が対象であることを個別通達でも伝えます。`announced_at` には周知に使った通達のID（`notice_id`）が要ります。
3. **同意を取る** — ⏳ **10 / 12**。初回ログインの直後に `/consent` が入ります（版が上がったときも再同意）。**在籍者が1人でも未同意なら開きません。**
4. **施行日を過ぎてから開く** — ⏳ **2026-08-10 施行**。3つが揃うと `v_support_quality` が行を返します（`RLS.md` §4「例外」）。周知（8/1）から施行まで9日あります。
5. **書けなかったら** — この画面だけを落とします。平均レスポンスは本人にも見える数字なので残せます。落ちるのは「返答内容の確認」だけで、他の設計機能は動きます。

### いま入っている値

```sql
insert into policy_documents
  (clause, version, revised_at, effective_from, announced_at, announced_by, notice_id)
values
  ('work_rules_art6', '第2版', '2026-07-28', '2026-08-10',
   '2026-08-01 10:00+09', '<小畑さんのuuid>', '<8/1の全体通達のuuid>');
```

`effective_from` が未来日のあいだ、`policy_gate_open('work_rules_art6')` は false を返します。**周知が済んでいても、施行前は開きません。**

## 4. 実装のゲート（3条件）

`announced_at` が入っただけでは開きません。周知は一方通行なので、受け取った側の記録が要ります。

```
policy_documents
  id             uuid pk
  clause         text unique   -- 'work_rules_art6'
  version        text          -- '第2版'
  revised_at     date
  effective_from date              -- 附則の施行日
  announced_at   timestamptz null  -- 周知が済むまで null
  announced_by   uuid fk users
  notice_id      uuid fk notices   -- 周知に使った全体通達（必須）
  revoked_at     timestamptz null  -- 停止の求めに応じたとき

policy_consents
  id                  uuid pk
  user_id             uuid fk users
  policy_document_id  uuid fk policy_documents
  consented_at        timestamptz
  device_token        text            -- どの端末で同意したか
  unique (user_id, policy_document_id)
```

**新しいテーブルは `policy_consents` だけです。** 同意も版の管理も、既存の `policy_documents` に紐づけます。

```sql
create or replace function policy_gate_open(c text) returns bool as $$
  select exists (
    select 1 from policy_documents d
    where d.clause = c
      and d.announced_at is not null          -- 1 周知した
      and d.notice_id  is not null            --   通達を出さずには立てられない
      and d.revoked_at is null
      and d.effective_from <= current_date    -- 3 施行日を過ぎた
      and (select count(*) from policy_consents pc
           where pc.policy_document_id = d.id)
          = (select count(*) from users where retired_at is null)   -- 2 同意 100%
  );
$$ language sql stable security definer;
```

- 3つのうち1つでも欠けると、`v_support_quality` は行を返しません。
- 画面（`12f`）は同じ条件でロックし、残っている条件を表示します。UIのロックは説明のためのもので、**担保はRLS側です。**
- 解錠は「フラグを立てる」操作ではありません。周知の実績と、受け取った側の同意と、施行日の到来で自動的に開きます。

### 未同意の見せ方

運営者の画面には **「未同意 2名」と件数だけ** 出します。**誰が未同意かは出しません。** 名指しできる形にすると、同意が同意でなくなります。催促は全体通達で行います。

### 分母は在籍者だけ

退職で分母が減れば開きます。入社で増えれば、**その人が同意するまで閉じます。** 入社時の同意は初回ログインで取れるので、通常は数分です。

## 5. 同意（`/consent`）

初回ログインの直後、および規定の版が上がったときに入ります。**同意しないと本体に入れません。抜け道は作りません。**

載せる5項目（`13a`）：

1. **記録されるもの** — 施術の記録、before/after 画像、相談と返答、到達の判断、操作履歴（第4条）
2. **誰が見られるか** — 可視領域8区分の要約（第3条第3項・別紙「可視領域一覧」）
3. **指導内容の確認について** — 次の文言をぼかさずそのまま出します：

   > 指導の質を保つため、指導者から従業員への返答内容と返答日数を、運営者が確認することがあります。この確認は個別に通知されず、閲覧履歴にも表示されません。目的は指導体制の見直しに限られ、個人の評価には使いません。確認の停止を求めることができます。

4. **評価に直結しないこと** — 第2条第2項。時間外に書く義務もないこと（第2条第3項）
5. **退職後の扱い** — 共有した記録は氏名を外して残る（`Other`）／習熟の経過・能力の記録・相談は削除（第8条）

下部固定：チェックボックス「内容を確認しました」＋ ボタン「同意して開始」。「規定の全文を読む」→ `/policy`。

版が上がったら受信ボックスに1件（`source_kind = 'policy_update'`）＋次回ログインで再同意。差分を先頭に示します。

## 6. 全文（`/policy`）

条文9条の全文。**全役割から到達できます** — Staffは「役割」画面、Support / Managementは「設定」の中。版・施行日・自分の同意日時を表示し、過去の版も読めます。

---

## 7. 例外の外側（変えないこと）

- 平均レスポンスの**数値**は、Capability Mapの「誠実さ」として本人にも見えます。例外にするのは返答の**内容**の閲覧だけです。
- 個別通達に添えられるのは数字だけです（`attached_metrics`）。返答文の列がないので、引用は物理的にできません（第6条第5項）。
- Practice記録の閲覧（`record_views`）は例外ではありません。Managementが見たことも本人に出ます。
- Supportの他店舗ログインも例外ではありません。`store_access_log` に残り、双方の監査ログに出ます。
- **`/consent` と `/policy` の閲覧は例外ではありません。** 誰がいつ同意したかは本人にも運営者にも見えます。
