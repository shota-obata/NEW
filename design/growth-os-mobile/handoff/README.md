# Handoff: Growth OS Mobile（AI,re 社内育成OS）

## Overview

美容サロン AI,re の社内育成OSのモバイルアプリ。3つの役割（Staff / Support / Management）が同じ1つのシステムを別の入口から使う。

中心にあるのは「評価」ではなく「判断のループ」。Staffが問いを立て → 経験を記録し → ズレた判断を書き → Supportが答えではなく問いを返し → Growth OSが条件を数え → Supportが実務での成立を判断して到達が決まる。Managementは人ではなく設計（担当・シフト・介入量）を扱う。

**このパッケージのゴール**：この設計をそのまま実装できる状態にする。画面仕様・データモデル・権限マトリクス・通知ルールが揃っている。

## About the Design Files

同梱のHTMLは **デザインリファレンス** です。プロダクションコードとしてそのまま出荷するものではありません。

- `Growth OS Mobile (standalone).html` — ブラウザで開けば全画面を触れる単体ファイル。仕様確認用。
- `Growth OS Mobile.dc.html` — ソース。画面の値（色・字寸・余白・コピー）はここから正確に読めます。
- `ios-frame.jsx` / `support.js` — プレビュー用の枠と実行環境。実装には不要です。

タスクは、これらの画面を **対象コードベースの環境（React / Vue / SwiftUI / ネイティブ等）で再現する** こと。環境がまだ無い場合は、モバイルWeb（PWA）を推奨します。理由は後述。

## Fidelity

**High-fidelity（hifi）**。色・字寸・余白・角丸・状態変化まで確定しています。ピクセル単位で再現してください。ただしフォントは Georgia（見出し）＋ システムサンセリフ（本文）という指定で、日本語は Hiragino Sans / Noto Serif JP にフォールバックしています。iOSネイティブで作る場合は見出しに明朝系セリフ、本文にSF Proを当てるのが同等です。

## 実装の前提（重要な6点）

1〜3は画面と規定に落としてあります（デザインドキュメントの `12a`〜`12g`）。**そのまま実装してください。**

1. **認証は「端末登録 ＋ 個人ID ＋ 4桁PIN」です。** 4桁は1万通りしかないので、それ単独では業務データに弱い。未登録の端末からは、PINが正しくても入れません（PINの入力欄にも到達しません）。登録は Management発行のコード（6桁・15分・1回限り）→ 端末名と所有形態 → PIN。共有端末ではパーソナルスペースの「裏」を置かず、無操作3分で自動サインアウトします。**1人3台まで**、**PINは5回失敗で15分ロック**（解除はManagementのみ）。失効はManagementが理由付きで行い、本人に通知されます。→ `PERMISSIONS.md`「端末」／画面 `12a` `12b` `13e`
2. **可視領域はサーバ側（RLS）で担保します。** `PERMISSIONS.md` の8区分がそのままポリシー（`p01_`〜`p08_`）になっています。「Managementに相談本文を渡さない」は、UIで隠すのではなく **`body` 列を持たないビューにだけ権限を与える** 形です。「見えない」の返し方は3つだけ（404 ／ 空配列 ／ 列を落としたビュー）。403は返しません。→ **`RLS.md`**／画面 `12c` `12d` `12e`
3. **監査ログの例外1つは、社内規定に書いてから開きます。** Managementの「閲覧」画面（Support→Staffの返答の質）だけは、当人たちの閲覧履歴に載りません。根拠は **就業規則 第6条第1項**、開示からの除外は **第6条第3項**（第5条第1項の対象外）。条文の出典は `就業規則 追加条文 草案.dc.html`（全9条）に一本化しています。**周知・在籍者全員の同意・施行日の3つが揃うまで** `v_support_quality` は行を返さず、画面もロックされたままです。**社労士の確認を通してから開けてください。** → **`POLICY_INTERNAL_RULES.md`**／画面 `12f` `12g` `13c`
4. **規定への同意がないと、本体に入れません。** 初回ログインの直後と、規定の版が上がったときに `/consent` が入ります。抜け道は作りません（担保はセッションのDBロール）。条文9条の全文は全役割から読めます。→ `POLICY_INTERNAL_RULES.md` §5・§6／画面 `13a` `13b`
5. **時間外・定休日に通知は飛びません。** 就業規則 第2条第3項に合わせ、プッシュと催促は営業時間内のみ。AI,re は 月・水・木・金 11:00–20:00 ／ 土・日 10:00–19:00 ／ **火曜が定休日**です。時間外・定休日の記録作成は止めませんが、画面に1行出します。**定休日の練習は本人希望のみで、必要ペースの分母に数えず、Growth OSが提案・催促することもありません。** 練習枠は営業日の営業時間内から出します（例：月曜 11:00–12:00）。→ `DATA_MODEL.md`「営業時間（AI,re 確定値）」／`NOTIFICATIONS.md`／画面 `13d` `14c`
6. **同意を急がせる導線を作りません。** 未同意者への催促は全員宛の同じ文面だけで、宛先を絞る・人数を書く・期限を切る の3つはUIにもAPIにもありません。上限3回。→ `NOTIFICATIONS.md`／画面 `14a` `14d`
4. **退職・削除で記録は消えません。** サロンに出したPractice記録は氏名を `Other` に置換して残します。消す場合は Management と Support の双方同意＋24時間保留＋理由の記述必須。

## 推奨スタック（環境が無い場合）

**モバイルWeb（PWA）＋ Supabase**。理由：

- 店舗の端末はiPhoneが混在し、App Store配布の運用コストを避けたい規模（1会社・数店舗）。ホーム画面追加で足りる。
- 認証・DB・ストレージ（画像）・プッシュがひと揃いで、権限を行レベルセキュリティ（RLS）で書ける。可視領域の表がほぼそのままRLSポリシーになる。
- 同梱HTMLの構造（役割ごとのナビ＋画面）をReactにそのまま移せる。

ネイティブが要件なら SwiftUI + 任意のバックエンドで問題ありません。可視領域はサーバ側で担保してください。

## 段階

1. **設計の検証（1〜2週）** — standalone HTMLを配って3役で触る。記録は既存手段で並行。
2. **小さく本番（1〜2か月）** — 認証・保存・通知・権限。画面は作り直さない。
3. **運用の取り決め** — 退職時の記録、PIN再発行、店舗追加、規定の周知と全員の同意（「閲覧」画面はこれが揃うまで開きません）。

## 決まったこと（画面 `13e`）

- **端末の上限台数** — 1人3台。4台目は発行できず、Managementが既存を失効させてから発行する。
- **PINの失敗回数** — 5回で15分ロック。人単位で数え、15分を待たない解除はManagementのみ。
- **共有端末の自動サインアウト** — 無操作3分（5分から短縮）。書きかけは下書きとしてサーバに残す。

**「閲覧」が開くのは、残る2つが揃ってからです。**

- **在籍者全員の同意** — いま 10 / 12。未同意が1人でもいるあいだは開きません（催促は名指しにしない全体通達で。画面 `14a`）。

それまで `v_support_quality` は行を返さず、Managementの「閲覧」はロックのままです。他の機能はすべて動きます。
